# Windows validation status

This document records the current Windows validation boundary. The 123-test D3D11 PlayMode run predates the current VFX color-space guard and the Editor Play / HDRP template adaptations; historical results remain labeled separately from current work.

## Confirmed

- Target environment: Unity 6000.6.4f1, Windows, URP or HDRP, D3D11. Bridge output is supported in Windows D3D11 Editor Play and Windows D3D11 Player. Edit Mode, D3D12 Bridge output, and macOS output are outside scope. The Unity Editor itself must be running D3D11; its active API should be checked through `GraphicsDeviceType`.
- A standard HDRP project was opened in Unity 6000.6.4f1 on D3D11, and an ordinary Cube was displayed by pressing Play in that project. The user confirmed the physical Looking Glass image was visible. The run reported 1721 completed frames, 48 views, 0 pending work, and an empty LastError. This verifies a real Editor Play-to-Bridge display path; it does not establish exhaustive image quality across all 48 views.

The Editor Edit Mode helper also passed, including rejection of `StartSession()` while not playing. These results cover managed Session validation and Edit Mode behavior; they do not establish Editor Play/replay or domain-reload lifecycle behavior.
- After the user stopped Play in the HDRP project, the Editor recorded Session `Idle`, output `Closed`, shutdown pending 0, and empty Session/output error fields. This is a stopped-state observation only; it is not a passing replay or domain-reload test.
- The Editor route has cleanup implementation for Play exit, assembly reload, and Editor quit. Stop/replay and domain-reload lifecycle tests are still pending; physical output visibility and the stopped-state observation do not establish those lifecycle cases.

## Reproduction boundaries

Run Unity validation with Unity 6000.6.4f1, `-force-d3d11`, and the project at `Tests/Pipelines/Unity`. The final integration command is `unity test E:/LookingGlassSDK/Tests/Pipelines/Unity --editor-version 6000.6.4f1 --mode PlayMode --report-format junit --output E:/LookingGlassSDK/.local/windows-improvement/final-d3d11-123.xml --timeout 1200 -- -force-d3d11`. Run native checks from `Native` with the repository's existing CMake and CTest configuration; enable the optional shared-resource probe with `-DLKG_D3D12_SHARED_PROBE=ON`. The D3D12-to-D3D11 result is a probe and does not establish Unity or Bridge D3D12 support.

To reproduce the Bridge fault scenarios, first build the dedicated fake runtime after the native full configuration: `cmake --build Native/build-worker-release --config Release --target lkg_fake_bridge_fault_runtime`. Run the existing validation Player with an absolute fake DLL and a unique absolute evidence directory, using one scenario at a time:

```text
BridgeWorkerValidation.exe --runtime-path <absolute fake DLL> --fault-mode init-delay --fault-delay-ms 15000 --evidence-dir <unique absolute dir> --quality preview --grd off --pipeline urp -force-d3d11
BridgeWorkerValidation.exe --runtime-path <absolute fake DLL> --fault-mode draw-release --fault-delay-ms 15000 --evidence-dir <unique absolute dir> --quality preview --grd off --pipeline urp -force-d3d11
```

These commands exercise only the dedicated fake DLL and native-call delays. Their cleanup and reconnection evidence is not evidence of physical display quality, hotplug behavior, or arbitrary hardware connection hangs. Keep the generated evidence under local build output; do not add it to Git.
