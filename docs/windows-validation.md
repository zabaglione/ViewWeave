> Audience: Unity and rendering developers. This is a dated research or validation record limited to the revision, platform, and conditions stated here; it does not establish support for other configurations. For current support and setup, see [Compatibility](compatibility.md) and [Getting started](getting-started.md). Browse the [Technical guide](technical-guide.md) or [User guide](user-guide.md).

Current shutdown status is summarized in [Shutdown validation](shutdown-validation-20261008.md): the tested URP Garden and HDRP VFX Editor runs completed Play, Stop, one `File > Exit` request, and natural exit code 0. The earlier access violations remain in the historical record with unknown causes; successful current fixtures do not establish that those incidents were fixed.

This document records the current Windows validation boundary. The 123-test D3D11 PlayMode run used an older package snapshot and predates the current VFX color-space guard and Editor Play / HDRP template adaptations; keep its results separate from current D3D12 integration evidence.

The HDRP default changed to isolated per-view histories. The current implementation has been exercised in the Metal Editor/Player scope below, but no Windows D3D11, D3D12, or Windows Player run has validated this new history path. Older Windows D3D11 measurements in this document belong to prior package snapshots/shared-camera behavior and are not evidence for the current default.

## HDRP isolated-view history validation (2026-10-10)

Unity 6000.6.4f1 Metal batch `GraphicsCompatibility` passed 52/52 with zero skips. This validates only the stated fixture and implementation checks; it does not validate Windows graphics APIs or prove pixel correctness for each HDRP effect.

In a separate "66 Full" observation, graphics-driver growth was 2451 MB and the RenderTexture descriptor estimate was 1287 MB. That observation used a temporary 8192 MB preview-copy budget; it is not the product default.
- In the connected Go scene review, the user reported that lighting and brightness returned and orientation and depth looked natural. This is bounded user feedback, not an exhaustive optical review.
- Separate macOS rendering-only Development/Release Players passed four-view history, shared exposure, retirement, and resource-budget checks. Windows Players and macOS Bridge/device Players remain unverified.
- Pixel correctness for SSR, SSGI, volumetric fog/clouds, Motion Blur, and TAA remains unverified. A test that preserves Volume settings is not a visual pass for those effects.

The production defaults are `IsolatedViewHistories` and `FollowScene`; the shared-camera adaptations are available only through explicit `SharedCameraCompatibility`. History Resource Budget defaults to 4096 MB and Maximum History Cameras to 256. The budget uses the larger of observed graphics-driver growth and estimated new or enlarged RenderTexture storage. In Release Players the driver-growth counter is zero; the descriptor estimate excludes unobserved buffers and driver overhead, so this is not a complete VRAM cap. The camera-count limit applies in Editor and Player builds. See the [full HDRP view-history record](hdrp-view-history-validation-20261010.md) for implementation and evidence details.

## Reproduction boundaries

The historical full integration command uses Unity 6000.6.4f1 and `-force-d3d11`: `unity test E:/LookingGlassSDK/Tests/Pipelines/Unity --editor-version 6000.6.4f1 --mode PlayMode --report-format junit --output E:/LookingGlassSDK/.local/windows-improvement/final-d3d11-123.xml --timeout 1200 -- -force-d3d11`. D3D12 Editor Play requires `-force-d3d12` when explicitly selecting the API and the project's absolute scene path in the Editor launch harness; do not add `-force-gfx-direct` or an automatic quit flag. Run native checks from `Native` with the repository's existing CMake and CTest configuration. The optional `-DLKG_D3D12_SHARED_PROBE=ON` target remains a standalone probe, not the production worker test.

To reproduce the Bridge fault scenarios, first build the dedicated fake runtime after the native full configuration: `cmake --build Native/build-worker-release --config Release --target lkg_fake_bridge_fault_runtime`. Run the existing validation Player with an absolute fake DLL and a unique absolute evidence directory, using one scenario at a time:

```text
BridgeWorkerValidation.exe --runtime-path <absolute fake DLL> --fault-mode init-delay --fault-delay-ms 15000 --evidence-dir <unique absolute dir> --quality preview --grd off --pipeline urp -force-d3d11
BridgeWorkerValidation.exe --runtime-path <absolute fake DLL> --fault-mode draw-release --fault-delay-ms 15000 --evidence-dir <unique absolute dir> --quality preview --grd off --pipeline urp -force-d3d11
```
