### Run4: isolated nine-condition memory characterization

Run4 used the repository-local isolated project with Unity 6000.6.4f1, D3D11, PlayMode, and a 128x96 tile at capacity 512. It completed nine conditions: VFX off, then the cloned graph's `generateMotionVector` setting off/on, each at 1, 2, and 8 views. Each condition sampled frames 1, 2, 4, 8, 16, and 32. The 4096 MB history budget stayed at its default. A separate 512 MiB process/raw-counter stop threshold was also kept active.

The on/off factor was a serialized graph-setting comparison, not a test of active motion-buffer load. The cloned URP output is alpha blended (`blendMode=Alpha`). The URP sub-output reports motion-vector support only for opaque blend mode (`VFXURPSubOutput.cs:10`); VFX Graph computes `hasMotionVector` from sub-output support, implementation, and the serialized setting (`VFXAbstractRenderedOutput.cs:78-85`), then only adds the MotionVector update feature when that result is true (`VFXAbstractParticleOutput.cs:222-228`). Thus under the run's default URP compile path, toggling `generateMotionVector` did not enable this feature for the alpha-blended output. No compiled descriptor or native allocation was captured. The setting-on condition therefore must not be read as motion vectors being enabled or as a motion-buffer memory comparison. Other per-camera VFX resources, such as sorting-related buffers, remain possible and were not isolated by this test.

For each VFX-on condition, the black-background pixel gate captured output with the effect enabled and then with its renderer disabled. Every tile exceeded the 20-pixel difference threshold, and the renderer-off image had zero nonblack pixels. The smallest differences were 184 and 188 pixels for the two tiles in the 2-view motion-off case. All nine conditions found the expected history-camera count and `AntialiasingMode.None`; cleanup samples at frames 2, 4, and 8 found zero history cameras and destroyed owned quilt/driver/effect resources. No condition reached the 8 MiB continued-growth stop rule.

The fail-closed Win32 `GetProcessMemoryInfo` reader returned nonzero private bytes and working set throughout; earlier zero values from the managed `Process` API were not treated as memory measurements. Across 54 frame samples, the raw graphics counter did not change from frame 1 to frame 32 within any condition. Separately, from the global test-start baseline, raw graphics-counter growth peaked at 5,134,564 bytes and process-private growth at 164,261,888 bytes, below the 512 MiB stop threshold. The SDK per-condition history graphics high-water mark peaked at 589,824 bytes, and its texture estimate at 196,608 bytes; these are separate counters and are not the global raw-counter delta.

A root-owned, read-only Windows GPU process-memory sampler recorded 23 approximately one-second samples from startup through Editor exit. Its sampled maxima were 82,792,448 dedicated bytes, 47,984,640 shared bytes, 136,904,704 committed bytes, 1,625,202,688 process-private bytes, and 1,327,484,928 working-set bytes. The samples are not aligned to exact Unity frames, do not represent instantaneous peaks, and are not a fixture hard-stop monitor. Dedicated/shared process counters are not a physical VRAM total. These small-fixture observations do not explain or reproduce the reported 54,473 MB incident.

The nine conditions ran sequentially in one Editor process, so graphics-pool state may carry between conditions; they are not independent cold starts. Each condition observed only 32 frames. The motion-vector comparison was not an effective-feature or native-buffer comparison, and no compiled descriptor or native motion allocation was measured. No 48-view heavy sample, long-duration run, user-scene Preview-to-Play transition, or device output was tested.

### Source-side capacity context

Read-only inspection of the saved URP learning scene found a reference to `SampleSDF.vfx`; that asset stores particle capacity 345,000, strip capacity 2,300, and motion-vector generation enabled (`E:/URPSample_6.6.41f1/Assets/Samples/Visual Effect Graph/17.6.0/Learning Templates/VFX/SampleSDF.vfx`, lines 3440-3442 and 6097). Its `Strip URP` output is saved as opaque blend mode (around line 6092), but source inspection shows `implementsMotionVector=false` for this output hierarchy and the compiled `hasMotionVector` condition is false; the CPU descriptor inventory found no motion-vector buffer for this graph. The enabled authoring flag and opaque blend mode therefore do not make this asset an active motion-buffer candidate. The isolated run4 fixture was a different cloned graph at capacity 512. VFX Graph source contains a two-frame per-camera motion-buffer path for outputs that actually implement the feature (`VFXDataParticle.cs` lines 1192-1206 and 1263-1279), but neither that generic code path nor SampleSDF's saved setting proves a native allocation in the reported incident. It does not explain 54,473 MB.

The URP source also creates or updates cameras for all requested views in `UrpViewHistoryRenderer.cs` lines 88-117 before the per-view `BeginView` budget check at line 283; the after-view check is in `ViewScope.Dispose` around line 369. The 4096 MB setting is an observation threshold checked around view work, not a preallocation cap: setup allocations and allocations within the render call can occur before a later sample. These source details define the limits of this small fixture and are not a runtime fix or a causal finding.
