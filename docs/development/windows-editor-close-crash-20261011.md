# Windows manual Editor close crash dump and control diagnostics (2026-10-11 to 2026-10-12)

This record analyzes four distinct user-reported Unity Editor crash incidents: two reports associated with Editor close, one report whose trigger and quit phase were not captured, and one URP Preview-to-Play report. The initial incident is described in [`windows-environment-output-validation-20261011.md`](windows-environment-output-validation-20261011.md); the follow-ups occurred on 2026-10-12. They are separate from the automated HDRP drawing-only Player retry 7, which exited naturally before the first manual Editor process was created. The analyzed dumps identify a matching fault location, but do not establish its cause.
## Findings

The four incidents are user reports, not controlled crash reproductions. The analyzed dumps identify the Unity stdout/descriptor fault location `Unity!dup_nolock` at `0x44383df`; later dumps' full stacks were not obtained. Four controlled runs passed their scoped close and cleanup gates: one stopped-output control, two active Edit Preview closes under separate stdio configurations, and one active Play close. Three other attempts did not pass: a helper compile failure, a close sent to the wrong window followed by recovery, and a redirected-stdio run that failed its startup-handle gate. The final `-logFile -` comparison passed its three-pipe gate. The no-output, Unity-before-Bridge report, the unknown-phase report, and the URP memory-error report remain unresolved.

A separate native-only standard-handle probe was run once with the exact Bridge application active and once after the application was stopped and the three observed loopback listeners were absent at the pre-probe check. Both native runs loaded and initialized the production shim successfully and kept valid, same-object redirected standard handles. This does not reproduce an Editor crash or measure Unity's private CRT descriptors; the original crash startup streams remain unknown.

## Dump analysis

Read-only Minidump ExceptionStream and AMD64 context analysis found a write access violation (`0xc0000005`) at address `0x11f0`, with `ESI = 0xffffffff` (`-1`) and the instruction pointer in `Unity!dup_nolock`. The sanitized stack was:

```text
Unity!dup_nolock
Unity!dup
Unity!RedirectStdout
Unity!Application::Terminate
Unity!ContainerWndProc
```

The invalid descriptor state, fault address, and `dup_nolock` path match the prior stdout/shutdown fault family documented in [`windows-stdout-crash-20261011.md`](windows-stdout-crash-20261011.md). This locates the failure in Unity's stdout/descriptor shutdown path. It does not prove that Bridge or device output caused this instance. The current shim's first-load standard-handle snapshot/restore behavior does not establish the handle state at this later shutdown point.
