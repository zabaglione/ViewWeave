# URP VFX color and HDR output path investigation (2026-10-13)

This investigation concerns two reported differences between Game view and Looking Glass output: green GPU-event lamps appearing red, and rotating coins lacking the strong periodic highlight seen in Game view. Phases A and B measured different HDR target formats in a one-view URP Editor fixture and observed the green-mask difference with the original Bloom/ACES stack active. Phase C then removed that mask mismatch and substantially reduced the selected coin ROI difference by rendering the quilt view through a clone-only linear half-float HDR intermediate. This supports early HDR range loss in the off-screen quilt path as the cause of these fixture differences; the full user scenario and physical-device path remain unverified.

## User observations

The user reported that the green lamps in `Multi-StripsGPUEvents` appeared green in Game view but red on Looking Glass, while cables were moving and the three coins were rotating on Looking Glass during the same issue. The coins' periodic brightening in Game view was not reflected as a similarly strong highlight on Looking Glass. The later confirmation that cable and coin motion were visible makes a completely stale or wholly inactive Looking Glass output less likely. It does not show that the same VFX state, camera, color pipeline, or frame was used for both displays.

The project is the URP sample project `UNITY_PROJECT_1`, using Unity 6000.6.4f1 and URP/VFX Graph 17.6.0. The user reported using Quarter output and Editor Preview, then changing Output Quality from Preview to Balanced while in Play. The separate budget exception and shutdown crash are recorded in the [URP rendering incident report](windows-urp-vfx-rendering-incident-20261013.md); this color/HDR investigation does not assume that the budget exception caused either display difference or the crash.

## Source and asset findings

The VFX asset file `Assets/Samples/Visual Effect Graph/17.6.0/Learning Templates/VFX/MultiStripGPUEvents.vfx` contains the green and red event outputs. Its serialized asset `m_Name` is `MultiStripGPUEvents`; the graph's internal title is `Green Lights`, and one serialized node label is `Green Lights Quad` (asset line 23,800). These asset names are distinct from the scene GameObject label. The green HDR color value `(35.1144, 191.749, 0)` is serialized at asset line 24,284; the red value `(2.99608, 0.08146, 0)` is at line 27,062, with additive blending. These are source/asset values, distinct from captured runtime values after URP, camera targets, post-processing, or device transfer.

The saved scene's `VFX_SceneTemplate_AbstractBlue_URP` global-volume prefab has active/global enabled, weight 1, priority 47.95, and shared profile GUID `cced43bec9a2ba34fab82a55f08e509f`. The scene references the prefab through GUID `63ef69b6e69aad54ea304569805239cb`. Its `VFX_URP_Neutral` profile has Bloom enabled (threshold 2.5, intensity 0.6, scatter 0.7) and ACES tonemapping mode 2. In Phase B and C, the per-camera runtime VolumeManager stack observed from `AddRenderPasses` was valid on both normal and quilt paths and reported these Bloom values plus clamp 65472 and active ACES. This confirms the observed settings; it does not prove the individual pixel contribution of each post-processing component.

The saved normal/reference camera has HDR enabled, post-processing enabled, and TAA mode 3. The saved quilt target allocation in `QuiltRenderer` uses `ARGB32` at `Distribution/urp/ViewWeave/Core/Runtime/QuiltRenderer.cs` lines 696, 717, and 726. In the installed URP source, camera target selection reads `camera.targetTexture.graphicsFormat` in `UniversalRenderPipelineCore.cs` around line 1537 and propagates the selected format to the rendering descriptor around line 1604. HDRP uses a pipeline-asset color-buffer format through `HDRenderPipeline.GetColorBufferFormat()` (`HDRenderPipeline.cs:227-232`); RenderGraph color-buffer creation and HDRP post-processing intermediate creation both call this method (`HDRenderPipeline.RenderGraph.cs:2327-2337`; `HDRenderPipeline.PostProcess.cs:671`). This is a source-level pipeline difference, not evidence that it explains the user's separate HDRP sample result.

### Interpretation and limits

These measurements establish that the normal and quilt cameras used different target formats in this fixture and that the linear float readback retained over-1 values in the normal half-float target but not in the quilt UNorm sRGB target. This supports HDR range/target format as a likely contributor to the green-color and coin-highlight difference. It does not prove that the target-format difference alone caused the user's reported appearance, establish the precise clamp/encoding stage, or show what reached the physical display. Both probes disabled post-processing and TAA, used one view, and did not use Looking Glass hardware or native transfer.

The active Bloom threshold was observed as 2.5 with intensity 0.6, scatter 0.7, and clamp 65472; ACES tonemapping was active. Unity's Bloom source converts the threshold through `GammaToLinearSpace`; the per-pixel contribution and stage ordering relative to target conversion were not isolated. Do not infer a Bloom-source clamp at or below 1 from either the target format or saved profile. Specular reflection may also contribute to the coin highlight, but remains unconfirmed.

The normal target remained `R16G16B16A16_SFloat` (linear, sRGB false); the quilt target remained `R8G8B8A8_SRGB` (sRGB true). Both are bounded observation-harness passes, not feature-compatibility or physical-device passes. For the Green graph, Phase B reproduces a normal-green versus quilt-no-green mask result while native particles, matched cameras, PP flags, and the Bloom/ACES stack were observed. The result is consistent with a target-range/format contributor; it does not prove the exact stage or that the user’s physical display received these values. For the coins, the target/readback and temporal observations show a difference, but they do not establish the reported strong periodic highlight across all three coins or on the device. TAA, Quarter/12-view output, Looking Glass hardware, and native transfer remain untested. Memory guard thresholds were not reached, and these runs did not reproduce an Editor crash.

## Existing evidence and its limits

The earlier paired-view probes used one normal camera and one quilt camera at one view with AA and post-processing off. `Multi-StripsGPUEvents` generated GPU event particles in the longer run, but the strict green pixel classifier returned zero for both images and the NUnit result was inconclusive. `RotationAngle.vfx` passed a bounded image comparison with at most one pixel difference between normal and quilt images. Those probes neither enabled the saved HDR/PP/TAA settings nor used a physical device, and therefore do not test the current HDR-range hypothesis. The exact results and raw artifacts remain in the [prior incident report](windows-urp-vfx-rendering-incident-20261013.md) and its [probe archive](../validation/windows-urp-vfx-rendering-incident-20261013).

## Phase C: candidate HDR intermediate intervention

Phase C changed only a clone-local candidate URP package to render the quilt camera through a temporary `R16G16B16A16_SFloat` linear HDR intermediate. The final quilt output remains `R8G8B8A8_SRGB`; the candidate source and installed render source are preserved with hashes in the [Phase C archive](../validation/windows-urp-vfx-hdr-rootcause-20261013/phase-c). This is an experimental intervention, not a change to the SDK checkout or a released fix.

These one-view, 480 x 360, AA-off, PP-on clone comparisons provide causal evidence that preserving HDR range before the final quilt conversion addresses the two observed off-screen effects. They do not establish that the candidate is safe or correct for TAA, 12/48 views, broader effects, all hardware, or native/device transfer.

Accordingly, early HDR range loss in the URP off-screen path is supported as the cause of the reproduced fixture differences; the user’s complete Game-to-Looking Glass appearance is still unverified because the physical display and native transfer were not measured. No SDK production code was changed or released. The separate budget exception and Editor shutdown crash remain unresolved and are not attributed to this rendering cause. Potential next validation includes TAA at one view, Quarter/12-view output, and native/device transfer as separate stages; the candidate must remain isolated unless separately reviewed and validated.
